===============================================================================
2. WHO SETS THE UDC NAME (this is the crux)
===============================================================================
- The vendor rc uses property **vendor.usb.controller = "musb-hdrc"** (file:65, file:109).
- grep over the ENTIRE stock tree: **no rc file ever sets `sys.usb.controller`**.
- AOSP's system/etc/init/hw/init.usb.configfs.rc (shipped unmodified in system_a) only
  CONSUMES it:  file:23/29/39/… `write /config/usb_gadget/g1/UDC ${sys.usb.controller}`.
- The only stock component that sets `sys.usb.controller` is the vendor USB HAL:
    vendor/bin/hw/android.hardware.usb@1.2-service-mediatekv2
      strings: "sys.usb.controller"  "/config/usb_gadget/g1/UDC"  "/sys/class/udc/"
               "configfs setup not done yet"  "/config/usb_gadget/g1/os_desc/b.1"
    started as: service vendor.usb-hal-1-2 … (class hal)

=> CONFIRMED: `sys.usb.controller` is a RUNTIME value produced by the MTK USB HAL.
   CONFIRMED: the real UDC name is `musb-hdrc` (vendor.usb.controller, and
   /sys/class/udc/<name> is what the HAL scans).
   Also confirmed: base DTB usb0@11200000 compatible "mediatek,mt6765-usb20" -> MUSB,
   and the kernel Image carries the `cmode` / `cmode_show` / `cmode_store` sysfs attrs.

3. WHAT RECOVERY CURRENTLY DOES  (recovery/root/init.recovery.mt6765.rc, whole file)
===============================================================================
on init
    setprop sys.usb.configfs 1
    setprop sys.usb.ffs.aio_compat 1

on fs && property:ro.debuggable=0
    write /sys/class/udc/musb-hdrc/device/cmode 2
    start adbd

on boot
    … insmod touch modules …

MISSING vs stock (all confirmed absent from the repo):
  - write /sys/module/musb_hdrc/parameters/kernel_init_done 1        (stock file:2)
  - setprop sys.usb.controller musb-hdrc                            (nothing sets it in recovery)
  - mkdir /config/usb_gadget/g1 + descriptors + configs/b.1         (no gadget object at all)
  - mount configfs                                                  (no rc mounts /config)
  - mount functionfs adb /dev/usb-ffs/adb                           (stock file:83)
  - mkdir /config/usb_gadget/g1/functions/ffs.adb                   (AOSP rc does this, needs
                                                                     ${sys.usb.controller} later)
  - write /config/usb_gadget/g1/UDC musb-hdrc                       (the actual bind)
  - setprop sys.usb.config adb                                      (triggers the bind handlers)
  - the vendor USB HAL (not shippable in recovery; it is a full HIDL service)

`find recovery -iname '*usb*'` returns NOTHING, and grep over recovery/ + *.mk found no
gadget creation and no controller property. The ramdisk's generic TWRP
`init.recovery.usb.rc` is NOT in this repo, so its contents are UNKNOWN — but note that the
AOSP/TWRP-standard version of that file writes `${sys.usb.controller}`, which on this device
is only ever populated by the (absent) vendor HAL.

INferred root cause: no UDC is ever bound in recovery -> no ADB, no MTP, no USB mass storage.
Checks on device:
  ls /sys/class/udc/                       (expect musb-hdrc)
  ls /config/usb_gadget/g1/ ; cat /config/usb_gadget/g1/UDC
  ls /sys/module/musb_hdrc/parameters/
  dmesg | grep -iE 'musb|udc|gadget'

===============================================================================
4. UNVERIFIED / UNKNOWN
===============================================================================
- Effect of `write /sys/class/udc/musb-hdrc/device/cmode 2`. The `cmode*` attributes exist
  (kernel strings `cmode`, `cmode_show`, `cmode_store`, `[MUSB] cmode=%d, cable_mode=%d`),
  but the CDP/SDP meaning of the value 2 was not verified in the driver.
- Effect of `musb_hdrc.kernel_init_done` not being written in recovery. Stock writes it in
  `on early-init` (before anything else); the parameter exists in the kernel
  (/sys/module/musb_hdrc/parameters/). Its semantics were not decompiled.
- Whether TWRP's built ramdisk already contains a gadget script of its own (not in this repo).

NAME DISCIPLINE: `musb-hdrc` is a real, evidence-backed name (init.mt6765.usb.rc:65;
/sys/class/udc/ scan path in the HAL). Any other UDC name would be invention.
